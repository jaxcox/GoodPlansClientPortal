Behavior & Logic
Two top-level tabs
Coach (default) and Client. Clicking either resets the error state. Tab choice is local UI state only — not persisted.
Coach login
Hardcoded credentials: coach / coach123. On success, sets session to {type:'coach', name:'Coach'} and routes to Coach Admin.
Single shared coach account. No per-coach support yet.
Client login — Existing User
Looks up clients in storage by email + password AND activated === true. On match, session is set to {type:'client', clientId, name} and routes to Client Portal.
Client activation — First-time
Requires invite code (matched case-insensitive against client records where activated === false) plus an email and a chosen password. On activation, the client record is updated with the email/password and activated:true, then signed in.
Email is overwritten by the user's input — the email Coach entered when creating the client is replaced.
Session persistence
Session is stored at storage key portal:session. Reloads stay signed in until logout (which sets session to null).
Routing decision (App root)
No session → LoginPage. type==='coach' → CoachAdmin. Otherwise → ClientPortal with the stored clientId.
Seeded demo accounts
Three pre-activated client accounts seeded on first load: abc@demo.com / abc123 (ABC Autobody), docs@demo.com / docs123 (Doc's Auto Clinic), client@demo.com / client123 (Demo Company). Re-seeded if SEED_VERSION changes.
Planned Changes (for rebuild)
Add "Forgot password?" link to the Client Login tab (cross-reference)
Today there's no password recovery — if a client forgets their password, they're locked out. The full password reset flow is documented in Doc 04 PC #8 "Add password reset flow (coach-generated reset codes)". Doc 01 surface change: add a small "Forgot password?" link below the password field on the Client Login (Existing User) form. Clicking it opens the reset form: Email + Reset Code + New Password.
Reset code source: coach generates a 6-character single-use code from Coach Admin → client card → "Reset Password" action, and relays it to the client (text, email, in-call). 24-hour expiration.
Coach Login tab: no "Forgot password?" link — the coach is a single account; if you forget your own password, that's a different recovery path (likely "rebuild platform handles it" — see below).
See Doc 04 PC #8 for the full spec.
Replace plaintext passwords with proper authentication
Today, both coach and client passwords are stored in plaintext on records in browser storage (portal:clients for clients, hard-coded check for coach). Acceptable for the current prototype since data lives only in your browser, but unacceptable for any real deployment where the portal lives on a server and is accessed by multiple people.
Required for rebuild: proper password hashing (bcrypt or equivalent) + secure password verification. Plaintext passwords never written to storage, never returned in API responses, never logged.
Platform-neutral: whichever rebuild path you take — WordPress plugin, standalone web app on a real backend (Node + Postgres, Supabase, Firebase, etc.), or something else — proper auth comes built-in or via a well-tested library. Don't roll your own crypto.
Session handling: the current portal stores a session blob in browser storage (portal:session). The rebuild should use whatever session/token model the chosen platform provides (cookies, JWTs, etc.) — same outcome (logged-in state survives reload), much better security.
Migration path: demo accounts (coach/coach123, abc@demo.com/abc123, etc.) are seed data — they get re-created with hashed passwords on first run of the rebuilt app. No real client passwords to migrate yet.
Rate-limit invite-code and login attempts
Today, the login form will accept unlimited login attempts and unlimited invite-code attempts with no throttling. Combined with 6-character alphanumeric invite codes, this means a determined attacker could brute-force codes given enough time. Real-world risk is low at current scale (a handful of clients, no real value to attack), but the rebuild should add basic rate limiting.
Limits to apply: after N failed attempts (e.g. 5) within a short window (e.g. 5 minutes) on a single email or IP, lock further attempts for a cooldown period (e.g. 15 minutes). Same logic applies to invite-code and reset-code submissions.
Platform-neutral: whichever rebuild platform is chosen, this is standard. Most modern auth libraries / frameworks include rate limiting out of the box, or it's a small middleware layer.
Invite-code expiration: consider also adding an expiration date to invite codes (e.g. 30 days from generation). Codes that haven't been redeemed in that window expire and need to be regenerated. Reduces the window for guessing attacks and forces stale invites to be refreshed before client onboarding.
UX: on rate-limit hit, show a friendly message — "Too many attempts. Please wait a few minutes and try again." — not a technical error.
Note: current code behavior (above) is unchanged for now. These are notes for the eventual rebuild, not edits to apply today.
