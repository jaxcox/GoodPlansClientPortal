The Good Plans Co ABC Autobody
COACH VIEW Dashboard Weekly Entry Budget & Goals History Settings Back
Page body is identical to the Client View above — same Reporting Period card, same KPI sections, same capacity group entry blocks, same Notes, same Save button. Coach has full read/write access — can create new entries, edit existing ones, and overwrite by date.
Differences from Client View
(1) Yellow COACH VIEW badge in the top bar.
(2) Logout button reads Back and returns to the Coach Admin Clients list.
(3) Everything else identical — same data, same controls, full write access. Coach can backfill missed weeks, fix typos, or enter on the client's behalf when needed.
Why coach has write access
Intentional. Use cases include backfilling missed weeks during a coaching session, fixing data-entry mistakes, or capturing numbers in real-time during a 1:1. The coach is a trusted second pair of hands on this page, not a passive observer.
Behavior & Logic
Default starting date
On page load, entryDate defaults to currentMonday() — the Monday of the current week. The date picker accepts any date though; the user can change it freely.
Existing-vs-new behavior
When entryDate changes, the page looks for an entry with matching startDate. If found, all fields populate from that entry (including isPartial flag and days). If not, the form resets to a fresh entry with {startDate, days:7}.
Recent entries pills
Shows the 8 most-recent entries (sorted by date desc) as clickable pills. Active pill is highlighted yellow. Partial entries display their day count: "Mar 9 (3d)". Hardcoded to 8 — no pagination.
Auto-calc fields update live
As the user types in raw inputs, auto-calc fields (Gross Profit, GP%, Conversion, Avg Transaction, etc.) recalculate immediately and display in yellow with the AUTO badge. They're read-only — no input. The values aren't stored — only raw inputs are saved; auto-calcs are recomputed on every render.
Which fields appear
Per category, fields appear if (a) the KPI is always-on, OR (b) it's toggled in client.kpis, OR (c) it's an auto-calc whose dependencies are toggled. Inclusion rules differ slightly from the dashboard's getEnabledKpis() — see "Inclusion Reference" table below.
No subsections in Sales
Unlike the Dashboard (where Sales is split into Main / Estimating / Pipeline), this form renders all Sales fields flat in one 2-column grid. Pipeline Value, Estimates Written, etc. all sit side-by-side without subsection headers.
Capacity group blocks (Team)
Each capacity group renders a sub-block in the Team category. Block header shows group name + live-calculated utilization %. Inputs vary by method:
Manual: single Utilization % field.
Slots: Total Slots + Filled Slots (2 cols).
Labor Hours / Working Hours / Headcount: Labor Hours Completed.
By Dollars: Revenue ($).
Stored in entry.cgData[groupId].
Notes block
Free-text textarea, multi-line. Plain text only — no rich formatting. Placeholder: "Add any notes, context, or highlights...". Whatever the client types here surfaces on the dashboard's notes display when this entry is the displayed week.
Save behavior
On Save: filters out any existing entry whose startDate matches the current entryDate, then appends the new record. Result: date is the unique key. Saving over an existing entry overwrites it silently — no confirmation. Only raw inputs are saved (no auto-calc values, no pre-computed numbers). Storage path: portal:e:{clientId}.
Partial period rules
Partial Period toggle exposes a "Number of Days (1-6)" field, clamped to 1–6. The day count is stored as entry.days and flagged with isPartial:true. Downstream goals scale proportionally — e.g. weekly revenue goal becomes monthlyGoal × (days ÷ daysInMonth) instead of full-week. Used for opening/closing weeks, holiday breaks, or mid-week starts.
Industry relabels apply
Same relabeling rules as the Dashboard apply to field labels here:
Healthcare: "Leads" → "New Clients Scheduled", Util tile suppressed.
Construction: "New Clients" → "New Contracts (#)", Sales Close Rate becomes auto-calc (read-only) since it's derived from contracts $ ÷ proposals $.
Empty categories hide
If a category has no enabled standard KPIs, no custom KPIs, and no capacity groups (for Team), the entire category card is hidden — no header, no empty state. Keeps the form focused on what the client actually tracks.

Custom KPIs render alongside standard ones in their assigned category. Always-on, always editable (or % auto-aggregated for display only — but on this entry form, all custom KPIs are user-input).
Saved Entry Shape
Each saved entry is a flat object on the array stored at portal:e:{clientId}: 
{
  startDate: "2026-04-20",     // unique key
  days: 7,                      // 1-7
  isPartial: false,
  revenue: "20100",             // raw user input — strings, not numbers
  cogs: "11055",
  leads: "19",
  newClients: "11",
  newContractsDollars: "18000",
  // ... other toggled-on KPI fields
  notes: "Strong week — closed two big jobs.",
  cgData: {                     // capacity group inputs, keyed by group id
    cg_prod: { laborHoursCompleted: "156" },
    cg_sales: { revenue: "47000" }
  }
}
Auto-calc fields are not stored. GP, GP%, conversion rates, etc. are recomputed every render via calcEntry(entry, client). This means raw inputs are the source of truth — if a formula changes in code, all historical entries reflect the new formula immediately.
Planned Changes (for rebuild)
Snap Period Starting Date to Monday
The date picker currently accepts any date. Since entries are conceptually weekly, snap any picked date to the Monday of that week — so picking Wednesday Apr 22 silently becomes Monday Apr 20. Removes the case where two entries land in the same week with mismatched start days, which would break weekly comparisons silently.
Exception: Partial Period entries can start mid-week (that's the point — opening or closing weeks, holiday breaks). Snap-to-Monday only applies to Full Week.
UX: Show a brief inline note when the snap happens: "Adjusted to Monday Apr 20", so it's not a silent change.
Carryover from Doc 04 / 05 — Sales structure
Doc 04 and Doc 05 carry the planned change to flatten the Sales card and drop the Estimating subsection on the Dashboard. On Weekly Entry, Sales is already flat — no subsection headers — so no visual change is needed here. If the Estimating-related KPIs themselves are removed (estimatesWritten, proposalsDollars, avgEstimateValue), they'd disappear from this entry form's Sales section accordingly. Tracking here so it's not forgotten when the Sales decision lands.
No-entry banner lands here
Per Doc 03's planned change for the no-entry indicator: when a client logs in and the current week's entry is missing, a red banner appears on the Dashboard with a "Go to Weekly Entry" button. That button lands the user here, with the date pre-set to the current Monday and a fresh form. No special treatment needed on this page — the existing default-to-currentMonday behavior already handles it. Noting for cross-doc traceability.
Cancel button on Weekly Entry
Add a Cancel button next to each Save Entry button (both the top-right and bottom-right placements). Always active on any entry screen — whether the user is editing an existing entry or starting a fresh one.
What it does: reloads the form from whatever's saved at the current entryDate. If a saved entry exists for that date, the form reverts to its saved state — any in-progress edits are discarded. If no saved entry exists, the form clears back to the default empty state ({startDate, days:7}).
Confirmation: if there are unsaved changes, show a confirm dialog — "Discard your changes?" with Cancel / Discard buttons. If nothing has changed, Cancel is a silent no-op.
Styling: secondary/grey button so Save Entry remains the primary action. Cancel sits to the left of Save in both placements.
Coach view: same — Cancel works identically when the coach is editing on a client's behalf.
Resolves: the silent-overwrite scenario where a client opens an existing entry, accidentally clears or alters fields, then saves before noticing — Cancel gives them an explicit way to revert before saving.
Delete entry capability
Currently no way to remove a saved entry from anywhere in the portal — once saved, an entry persists until storage is edited manually. Add a delete affordance so a client (or coach) can remove a bad entry — wrong date, duplicate, test data, etc.
Where it lives: Weekly Entry only. When a saved entry is loaded (i.e. the current entryDate matches an existing entry), show a small "Delete this entry" link below the Cancel/Save buttons. When a fresh entry is loaded (no match), the link is hidden — there's nothing to delete.
Not on History: History stays read-only. The KPIs-as-rows / dates-as-columns layout doesn't lend itself to a row-level delete anyway — the deletable thing is a column, not a row. Single delete path keeps the UX unambiguous.
Confirmation: required. "Delete the entry for [date]? This can't be undone." with Cancel / Delete buttons. Delete is destructive and irreversible — no soft-delete or undo in v1.
What gets deleted: the entry record at that date. All raw inputs and capacity-group data for that date. Auto-calculated values aren't stored, so nothing else cascades.
After delete: form resets to a fresh entry for the same date (the date stays selected, but it's now an unsaved blank). Recent-entries pills refresh — the deleted date drops off the strip.
Coach view: coach can also delete — same access pattern as the rest of Weekly Entry.
Persistent "Saved ✓" state across all save buttons
Save buttons currently flash green for 2 seconds after a successful save, then revert to the yellow "Save" state. Replace that with a persistent saved state: the button stays green and reads "Saved ✓" until the form is meaningfully changed or the user leaves the current edit context.
Scope: applies to all save buttons across the portal — Weekly Entry, Budget & Goals, Settings, Custom Industries Manager. Wherever there is a Save button, this behavior applies.
Cancel buttons paired everywhere: wherever there is a Save button, there is also a Cancel button next to it (secondary grey styling). Same revert-to-saved-state behavior — discards in-progress changes and reverts to the most recently saved state.
Reverts to active "Save" state when: (a) any field on the form is edited, or (b) the user leaves the current edit context (navigates to a different page, switches to a different entry date on Weekly Entry, switches to a different budget year on Budget & Goals, logs out, etc.).
Saved state is per-entry / per-edit-context: on Weekly Entry, the saved state is tied to the current entryDate — switching to a different date resets the indicator since you're now editing a different entry. Same idea on Budget & Goals when switching budget years.
Cancel during clean-saved state: active no-op — the button stays clickable but does nothing since there are no unsaved changes to discard. No confirm dialog.
Rationale: the 2-second flash is gone before the user has time to verify it. A persistent indicator gives clear, unambiguous feedback about whether their work is currently saved.
Unsaved-changes guard on navigation and date switching
When the form has unsaved changes, attempting to leave the current edit context (clicking a different recent-entry pill, picking a different date in the date picker, navigating to another page like Dashboard or History, or logging out) opens a small confirmation dialog before the navigation completes.
Dialog content: headline reads "You have unsaved changes." Three buttons: Save (commits the current form, then proceeds with the navigation), Discard Changes (drops the in-progress edits and proceeds with the navigation), Stay Here (cancels the navigation and keeps the user on the current edit).
Scope of "navigation": any action that would switch the user out of the current edit context — Weekly Entry includes pill clicks, date picker changes, top-nav clicks, and Logout. Budget & Goals includes year switching and top-nav clicks. Settings and Custom Industries follow the same pattern.
No dialog when nothing has changed: if the form is in a clean saved state, navigation proceeds silently — no interruption.
Pill creation tied to save: if a client opens a fresh entry for a new date, fills in some fields, then hits Cancel or chooses Discard Changes from the dialog, no recent-entry pill is created for that date. Pills are derived from the saved entries array — unsaved drafts are invisible. (This is already current behavior, called out here so it stays consistent through the rebuild.)
Coach view: same — coach gets the same dialog when navigating away from unsaved client data.
Block future dates on Weekly Entry
The date picker currently accepts any date — including dates years in the future. Cap the picker at the current Monday so a client cannot accidentally enter "Apr 28, 2027" or any week that hasn't happened yet.
Maximum allowed date: the current Monday (i.e., currentMonday()). Any later date is blocked at the picker level.
Past dates remain open: no minimum date constraint. Clients legitimately need to backfill missed weeks, and mid-year-intake clients may want to capture history before they joined.
Implementation: set max attribute on the date input to currentMonday(). Browsers handle the UI — picker grays out future dates.
Recent-entries pills unaffected: the pills only show entries that already exist, so future dates can't surface there anyway.
Prevent period overlap between entries
Block saving an entry whose date range overlaps with an existing entry. Stops the data-integrity issue where, e.g., a 7-day entry starting Apr 13 and a 3-day Partial entry starting Apr 15 both save and both feed cumulative aggregations — double-counting the overlap.
Logic: on save, compute the date range of the entry being saved (startDate through startDate + days − 1). Compare against the date range of every other saved entry. If any overlap exists, reject the save.
Exception: overwriting an entry that has the exact same startDate is allowed — that's "edit existing entry," not "create overlapping entry."
Error message: inline near the date picker — "This period overlaps with your entry starting [date]. Edit that entry instead, or pick a non-overlapping date." Includes a clickable link to jump to the conflicting entry.
Common cases this prevents: (1) Full Week and Partial Period entries overlapping in the same calendar week. (2) Two Partial entries that abut or overlap. (3) Backdated entries that collide with already-recorded weeks.
Mandatory fields: Revenue and COGS
Revenue and COGS become required fields on every weekly entry. Save is disabled until both are filled. Empty mandatory fields show a red outline. Zero is a valid value — clients can save a $0 revenue week if they had one (closed, holiday, etc.) — but the field cannot be left blank.
Why these two: Revenue is the anchor for nearly every goal, color rule, and cumulative calc on the dashboard. COGS feeds Gross Profit and GP% — both always-on KPIs. An entry without these is essentially blank and pollutes downstream views.
All other fields stay optional: requiring everything would be too aggressive. Clients legitimately have weeks where they didn't run estimates, didn't complete jobs, etc. — they shouldn't be forced to type "0" everywhere.
Visual treatment: required fields show a small red asterisk after the label (e.g. "Revenue *"). When empty and the user attempts to save, the input border turns red and a brief inline message reads "Required." Save button stays disabled until the field has a value.
Future extension (v2): individual clients could mark additional KPIs as required in their settings — useful for, e.g., a Construction client who wants Labor Hours required every week. Out of scope for v1.
Cancel still works regardless: Cancel reverts the form even if mandatory fields are empty. Mandatory only blocks Save, not Cancel.
Sun–Sat week change (carry-forward from Doc 08)
Portal-wide week boundary changes from Mon–Sun to Sun–Sat. See Doc 08 for the source-of-truth decision and full cross-doc impact list.
Date picker default: "Period Starting Date" defaults to the current Sunday instead of the current Monday. Combined with the existing planned change "Snap Period Starting Date to Monday," the snap target becomes Sunday. Update that earlier card's wording during the rebuild pass.
Recent-entries pill strip: dates displayed are now Sun–Sat anchored. Each pill shows the week's Sunday date.
Partial-entry boundary logic: when a week crosses a month/quarter/year boundary, the split logic still produces two partials (e.g. a Sun–Sat week spanning Mar 30 → Apr 5 splits into a 2-day March entry and a 5-day April entry). Boundary-driven, calendar-agnostic — no code change needed beyond the anchor shift.
Helper functions: currentMonday() usage replaced with currentSunday() throughout.
Existing data migration: entries already saved with Monday startDate values get re-anchored (subtract one day) or remain as-is via a cutover date. Approach decided when the rebuild lands; documented in Doc 08.
