MTD, QTD, and YTD share one structure; mode-specific differences are called out inline.

Mode-Specific Differences
Aspect MTD QTD YTD
Period definition Current calendar month, 1st through today. Current calendar quarter, first day of quarter through today. Current calendar year, Jan 1 through today.
Period label "April MTD" — full month name + MTD. "Q2 QTD" — Q + quarter number + QTD. "2026 YTD" — year + YTD. Plus pill: "incl. actuals thru April" when YTD actuals are set.
Entries included Entries whose startDate month matches current month. Entries whose startDate quarter matches current quarter. Entries whose startDate year matches current year.
YTD actuals integration Not integrated. MTD always reflects only this month's entries. Integrated only when ytdThruMonth falls in or before this quarter and the current month is past ytdThruMonth. Adds YTD actuals to revenue/COGS/GP. Always integrated when ytdThruMonth is set. YTD actuals (revenue + COGS) added to the cumulative roll-up.
Revenue goal scale Month's adjusted goal (getAdjMonthGoal) — accounts for seasonal % and YTD recovery if applicable. Sum of three months' adjusted goals (or revGoal × quarter fraction). Full annual revGoal.
Other-KPI goal scale Monthly goal × 1. Monthly goal × 3. Monthly goal × 12.
Total weeks in period Days in month ÷ 7. Days in quarter ÷ 7 (~13). 365 ÷ 7 (or 366 in leap years), ≈ 52.
Gap-to-Goal tile label "Revenue Needed This Month" "Revenue Needed This Quarter" "Revenue Needed This Year"

Mode selection is per-session, per-client
Mode (Weekly / MTD / QTD / YTD) lives in component state — resets to Weekly on every page load. Not persisted to the client record. Same behavior in client and coach view. Coach reviewing multiple clients: each client portal opens in Weekly regardless of the mode used on the previous client. Coach toggles mode per client. Intentional — keeps the default predictable.
Behavior & Logic
Mode selector
Four-button toggle in the dashboard header: Weekly · MTD · QTD · YTD. Active button is highlighted yellow. Default is Weekly. Selection lives in useState — resets on page reload, no persistence.
Which entries roll up
Per entryInPeriod(entry, mode, year, month, quarter): entry must match the current year, and startDate must fall in the current month (MTD) / quarter (QTD) / year (YTD). Future-dated entries (date > today) are also excluded — only "today and earlier" entries count.
Aggregation method per KPI
Defined per KPI on KPIS[].agg: sum (Revenue, Leads, Jobs, etc.), avg (On-Time Delivery, Close Rate non-Construction), last (Pipeline Value, Pipeline Deals, Accounts Receivable — point-in-time), derived (recomputed from raw aggregates: GP, GP%, Conversion, etc.). Custom KPIs sum if format is # or $, average if format is %.
Pace fraction
paceFrac = currentWeeks ÷ totalWeeksInPeriod, capped at 1.0. currentWeeks = number of saved entries in period, plus YTD-actuals weeks coverage when applicable. totalWeeksInPeriod: month days/7, quarter days/7, or 365/7 depending on mode. The pace fraction scales the full goal down to "what should be done by today."
Full goal vs pace goal
Each tile carries two numbers: fullGoal (the period total target) and paceGoal (full × paceFrac). Sum-aggregated KPIs scale; %, avg, last, and derived KPIs use the same value for both (no scaling — a 60% conversion rate is 60% whether you've completed 1 week or 12).
Tile color — against pace goal
Color compares actual to pace goal, not full goal. Green when at-or-above pace (or at-or-below for inverted KPIs); red when behind pace; gray when no goal exists. This means a tile turns red the moment the period falls behind, not only when the full target is missed.
"Achieved!" badge
Top-right corner of any tile where actual ≥ fullGoal (≤ for inverted). Independent of pace coloring — a tile can be green-on-pace without "Achieved!" until the full goal is met. Range KPIs (Accounts Receivable) never show the badge — they're not "complete-able." Two signals on purpose: color answers "are you on pace to hit the goal?", badge answers "have you hit the goal?" Green-without-badge means winning the race but haven't crossed the finish line; green-with-badge means crossed.
Progress bar (cumulative-only)
Each non-percent, non-range tile gets a thin progress bar above the goal line. Bar fill = min(actual ÷ paceGoal × 100, 100)%. Bar color matches the tile's pace color. Below the bar: "Pace: X · Goal: Y" with pace in the tile color, full goal in muted gray. Percent KPIs and range KPIs use the simpler "+/− X% vs goal" line instead.
Gap-to-Goal tile (Financials)
Appears once per cumulative dashboard, in the Financials category. Computes "how much more revenue is needed to hit the period's GP goal?" Formula: revenueNeeded = (gpGoal − gpActual) ÷ (gpMarginGoal ÷ 100). When GP is already at-or-above goal, shows "GP Goal Met!" in green. Requires GP goal, GP%, and current GP to compute — silently skipped if any are missing.
Cumulative-mode KPI exclusions
SKIP_CUM: laborHoursCompleted tile is hidden in cumulative modes. Employee Utilization: hidden when capacityMethod !== 'manual' — auto-calculated util across mixed weeks doesn't aggregate cleanly. Manual util still shows. Healthcare/Wellness employeeUtilization: always hidden, same as Weekly mode.
No week-over-week deltas
The ▲/▼ delta line under each tile value is Weekly-mode only. In cumulative modes there's no analogous "previous period" to compare against (last month's MTD doesn't have a clean meaning at any point mid-month).
YTD actuals integration
When budget.ytdRevenue > 0 and budget.ytdThruMonth is set, pre-coaching actuals get folded in. YTD mode: always added. QTD mode: added only if ytdThruMonth is in or before this quarter and the current month is after ytdThruMonth (i.e. the actuals overlap with this quarter). MTD mode: never. Affects only Revenue, COGS, GP, GP% — KPIs we don't have monthly historic actuals for. Pace weeks adjust accordingly: ytdActualWeeksCovered is added to currentWeeks.
Period label & YTD-actuals pill
Above the KPI grid: a single bold line showing "April MTD" / "Q2 QTD" / "2026 YTD". In YTD mode with actuals integrated, an additional small gray pill follows: "incl. actuals thru April".
Tile eligibility otherwise matches Weekly
Aside from the cumulative-mode exclusions above, the tile set comes from the same getEnabledKpis(client) source as Weekly. Industry relabels (Healthcare, Construction) apply identically. Sales is split into Main / Estimating / Pipeline subsections identically. Custom KPI tiles render in their assigned categories. Capacity group tiles (when present) replace the global Employee Utilization tile in Team.
Empty state
When no entries fall in the period, the KPI grid is replaced with a centered card reading "No entries for this period yet." Exception: in YTD mode with YTD actuals set, the actuals alone produce a partial revenue/COGS/GP roll-up — the grid renders, just sparsely.
Where goals come from
getPeriodGoalFull(id, budget, mode, month, quarter) resolves to: Revenue → adjusted monthly goal × month/quarter/year scaling; COGS → derived via cogsTargetPct; GP and GP% → derived from Revenue and COGS goals; everything else → budget.goals[id] (monthly value) × scaling factor (1, 3, or 12). All sourced from Budget & Goals (doc-05).
Range KPIs (Accounts Receivable) in cumulative modes
Range KPIs use agg:'last' — cumulative modes show the most recent entry's value, identical to Weekly mode. Technically point-in-time data doesn't have a "YTD AR" meaning, but coaches read AR as "current balance" regardless of mode, so the tile stays visible across all four modes. Same number, same color logic (within ±10% of target = green). Intentional redundancy — keeping the financial snapshot present in every view is more useful than the strict period-purity of hiding it.
Custom KPI direction handling
Custom KPIs with dir:'lo' (lower-is-better) invert color logic against the pace goal — green when actual ≤ paceGoal, red when above. Same as Cancellations and Warranty/Returns. isKpiInv() handles both built-in and custom inverted KPIs uniformly. "Achieved!" badge inverts the same way. Pace-goal scaling is correct: a monthly goal of 5 scales to 15 (QTD) or 60 (YTD), pace fraction applied normally.
Capacity group tile aggregation
When client.kpis.teamCapacity is on, per-group tiles render in the Team category. Cumulative aggregation: raw values are summed across in-period entries regardless of the group's metric (working hours, labor hours, revenue $). Tile displays the summed value (e.g. "1,800 hrs", "$47,000"). Full goal scales as capacity × totalWeeksInPeriod; pace goal uses elapsed weeks. Same color logic as other tiles — green when at-or-above pace, red when behind. Intentionally raw rather than averaged so a coach reading the tile sees actual produced hours / dollars instead of a derived percentage. Revenue-metric groups overlap with the company-wide Revenue tile by design — group tile is a sub-view of the same revenue.
No Notes block in cumulative modes
The per-entry Notes block (visible on Weekly mode under the most recent entry) doesn't render here. Cumulative views aren't tied to a single entry, so there's no single note to surface.
Planned Changes (for rebuild)
Pace fraction is time-based, not entry-based
Today's pace tells the user where they should be in the period regardless of whether entries exist. A client 3 weeks into a month who has only entered 2 of those weeks still has pace at 3 weeks, not 2. Separates "business performance" from "entry discipline" — the latter is handled by the Entry Overdue indicator (Doc 03 planned change).
Formula change: paceFrac = weeksElapsedInPeriod / totalWeeksInPeriod. weeksElapsedInPeriod is calendar-based, not entry-based.
Pace updates weekly, not daily. The "weeks elapsed" counter advances by 1 each time a new week begins. Pace is stable for 7 days at a stretch, then steps up. Cleaner read for the dashboard, no daily drift.
Low-coverage neutral state: when entries cover less than ~50% of elapsed weeks, suppress pace coloring on tiles and show a neutral state with a small note — "Low entry coverage — pace not meaningful." Prevents the false-catastrophe reading when a client is mostly missing entries. Threshold to be tuned.
YTD actuals: still contribute their week-coverage to weeksElapsedInPeriod in YTD/QTD modes the same way they do today.
Week definition changes — Sun–Sat instead of Mon–Sun
Switch the portal's week boundary from Monday-anchored (Mon–Sun) to Sunday-anchored (Sun–Sat). Affects every page that touches a week — entry dates, default ranges, "current week" logic, week-over-week comparisons, period-boundary partial entries.

Period-boundary partial entries — confirm behavior for all future years
Weeks that cross a month, quarter, or year boundary are already split into two partial entries (per Doc 06). Each partial belongs to its own period and is filtered/aggregated based on its own startDate. This logic derives period membership from the entry's actual date (getMonth(), getFullYear(), Math.floor(month/3)) and works for any year — no per-year configuration. Document and verify the behavior so it's clear it's intentional.
Month boundary (e.g. Mar 30 – Apr 5): splits into a 2-day March entry and a 5-day April entry. March MTD includes the 2-day partial; April MTD includes the 5-day partial. Confirmed correct.
Quarter boundary (e.g. Mar 30 – Apr 5): same split. Q1 QTD picks up the 2-day partial via its March startDate; Q2 QTD picks up the 5-day partial via April. Confirmed correct.
Year boundary (e.g. Dec 27, 2026 – Jan 2, 2027 under Sun–Sat weeks): splits into a 5-day December 2026 entry and a 2-day January 2027 entry. 2026 YTD includes the 5-day; 2027 YTD includes the 2-day. Verify: coach-facing labels and totals read sensibly — a year-end review should clearly show "the last 5 days of 2026 are in this YTD" without confusing the reader.
Leap years: totalWeeksInPeriod already handles leap years (366/7 vs 365/7). MTD uses actual days in month (handles February's 28 vs 29 correctly). QTD uses millisecond math between quarter start/end. Confirmed year-agnostic.
Calendar shift across years: with Sun–Sat weeks, 2026 and 2027 have different days-of-week on Jan 1, so partial-entry day counts shift. The split logic produces the right entries every year because it's driven by the calendar, not by hard-coded dates.
Action: no code change needed in current behavior. The rebuild should preserve this date-driven approach. Add a year-end test to the QA pass that confirms a Dec/Jan boundary week renders correctly on both years' YTD dashboards.
YTD actuals + entries overlap — warn the coach
When ytdThruMonth is set and weekly entries also exist within that same window (e.g. actuals through March + weekly entries dated in Jan/Feb/Mar), the cumulative rollup adds both — potentially double-counting revenue and COGS. Surface a warning on Budget & Goals so the coach can resolve it manually (delete the duplicate entries, shorten the actuals window, or leave it intentionally if they understand the trade-off).
No automatic exclusion: the system does not drop entries from the rollup. Coach decides.
Where the warning appears: on Budget & Goals, near the YTD Actuals card. Inline, not a blocking modal.
Trigger: any weekly entry with startDate on or before the last day of ytdThruMonth in the same year as the budget.
Wording (draft): "Heads up — N weekly entries exist within the YTD actuals window ([Jan–Mar]). The cumulative dashboard will add both these entries and the actuals total, which may double-count revenue. If that's not intentional, delete the entries or shorten the actuals window."
Cross-doc note: this is a Doc 05 (Budget & Goals) UI change driven by Doc 08 cumulative-mode behavior. When Doc 05 gets its next pass, add the corresponding planned-change card there.
YTD actuals stored month-by-month — hybrid entry on Budget & Goals
Replace single-bucket YTD actuals (ytdRevenue, ytdCogs) with month-by-month arrays. Solves the QTD-accuracy problem for clients starting mid-quarter (e.g. coach takes on a client in May with YTD actuals through April — Q2 QTD needs April's actuals separated from Jan–Mar). Keeps the fast-entry path coaches expect via auto-distribution.
Storage: ytdRevenueByMonth: [num|null × 12] and ytdCogsByMonth: [num|null × 12] on the budget record. Indices 0–11 = Jan–Dec. Months past ytdThruMonth are null. Migration: existing single-total values get auto-distributed and saved into the array on first load.
Default UI — single-total entry: coach sees the same two fields they see today (Revenue, COGS) plus the existing ytdThruMonth dropdown. Fast path stays fast.
Auto-distribution on save: when only the single total is entered, the system splits it across the covered months. Even split (total / monthsCovered) when seasonType='even'; weighted by seasonPct when seasonType='seasonal'. Same for COGS.
Optional detail entry: a "Show monthly breakdown" toggle (or expand control) opens a per-month grid below the single-total fields. One row per covered month with revenue + COGS columns. Coach can override any month inline. Edited months stay edited; un-edited months continue to track auto-distribution.
Sync rule: editing the single total re-runs auto-distribution, overwriting any prior overrides (with a warning). Editing a month's value updates that month and recomputes the single total as the sum. Two-way binding, with auto-distribution as the default direction.
QTD calculation: sum the months in ytdRevenueByMonth that fall in the current quarter. No more "is ytdThruMonth in or before this quarter and is current month past it" condition — replaced with a clean per-month sum.
YTD calculation: sum the entire ytdRevenueByMonth array (all non-null entries). Behavior unchanged from coach's perspective.
MTD calculation: if the current month falls inside the YTD-actuals window (rare — coach would only see this in their first few days before any current-month entries exist), MTD reads from the month's actual value. Otherwise unaffected.
Mid-quarter starts: a coach starting an August client only needs to override one month to get accurate QTD (Q3 = Jul + Aug + Sep; Jul falls in the YTD window). Five seconds of override work for accurate QTD, vs. zero seconds with auto-distribution that's "close enough."
Cross-doc note: this is a Doc 05 (Budget & Goals) UI and storage change driven by Doc 08 cumulative-mode behavior. Add the matching planned-change card on Doc 05 in the cross-doc pass. Also affects YtdStatusBanners math (Doc 05) — same total, just sourced from the array sum.
Pairs with the overlap warning above: when month-level actuals exist and a weekly entry also lands in the same month, the warning still fires. Resolution path is the same.
Day-weighted averaging for avg-aggregated KPIs + Close Rate derivation fix
Two related accuracy improvements to cumulative aggregation. Currently avg-aggregated KPIs use a simple mean across entries — a 3-day partial weights the same as a 7-day full week. And non-Construction Close Rate uses a simple-mean of weekly close rates, even though the underlying contract and estimate dollars are already collected per entry.
Day-weighted avg: replace simple mean with day-weighted mean for all agg:'avg' KPIs. Formula: Σ(value × days) / Σ(days). A 3-day entry at 100% and a 7-day entry at 80% averages to 86% (1060 / 10) instead of 90%. Affects: On-Time Delivery, Employee Utilization (manual mode), Labor Efficiency.
Close Rate derivation fix: non-Construction Close Rate currently aggregates as avg. Switch to derived: sum(newContractsDollars) / sum(proposalsDollars) — same formula Construction already uses. The underlying inputs are collected on every entry already; no new fields required. One-line code change.
KPIs that already aggregate correctly (no change): Gross Profit Margin (GP / Revenue recomputed), Conversion Rate (newClients / leads recomputed), all other auto/derived KPIs.
Custom KPIs: day-weighted treatment applies to fmt:'%' custom KPIs (currently simple mean). Sum-aggregated custom KPIs (Count, Dollar) unchanged.
Edge case — full-week-only client: when every entry is 7 days, day-weighted equals simple mean. No visible change for clients who never log partial weeks.
Capacity group aggregation: separate code path, sum-based, not affected.
Note: current code behavior (above) is unchanged for now. These are notes for the eventual rebuild, not edits to apply today.
