Page body identical to Client View — same cards, same fields, same edit access. Coach can change any setting on the client's behalf.
Differences from Client View
(1) Yellow COACH VIEW badge in the top bar.
(2) Logout button reads Back and returns to Coach Admin.
(3) Coach has full edit access to every section. No read-only state today.
In current code, client and coach have identical access

Behavior & Logic
Storage
All fields persist on the client record in portal:clients. Save writes the whole updated client object back to the array. No partial saves.
Save button (top & bottom)
Same Save button appears at top-right and bottom-right. Both call the same handler. Two buttons because the page is long enough that scrolling back up to save is annoying.
Industry change is destructive
Changing industry replaces client.kpis with that industry's defaults. Any toggles set manually for the previous industry are lost. Tooltip in the UI says "Changing industry resets KPI defaults."
KPI toggle visibility
Only KPIs that the selected industry's kpiDefaults contain a value for (0 or 1) appear as toggles. Auto-calculated KPIs (Conversion Rate, Avg Repair Order, etc.) and always-on KPIs (Revenue/COGS/GP/GP%) are not shown — they're managed automatically.
Active KPIs panel — Financials section appears conditionally
Only renders if the industry has any optional Financials KPIs (currently just Accounts Receivable in Construction). Industries without optional Financials KPIs skip the section entirely.
Capacity groups grouped by method
Groups using the same method are visually clustered under a method header. "+ Add" within a method header creates another group of that same method. The "Add Tracking Method" row at the bottom shows only methods not yet in use — clicking creates the first group with that method.
Capacity group methods (6 types)
Manual % — coach types in utilization % each week.
By Time Slots — total slots vs filled slots (e.g. Healthcare appts).
By Labor Hours — labor hours completed ÷ employee capacity.
By Working Hours — labor hours completed ÷ (FTE × hrs/wk).
By Revenue ($) — revenue ÷ revenue capacity.
By Headcount — labor hours ÷ headcount capacity.
Method-dependent fields
Each capacity group's edit panel changes shape based on its method:
Manual: no extra config.
Slots: 30 / 60 min slot duration toggle.
Labor Hours / Revenue: employee list with hours or $ capacity per row.
Working Hours: "Hours/Week per FTE" + department list (full-time / part-time counts).
Headcount: "Hours/Week per FTE" + FT/PT vs Labor Cap toggle + department list.
Custom KPIs are flat — added one at a time
Add row at top creates a new KPI in the list below. Clicking an existing row enters inline edit mode (form replaces the row). Save commits, Cancel reverts.
Custom KPI fields
Name (free text), Category (Financials / Marketing / Sales / Operations / Team / Overall Company), Format (Count / Dollar / Percent), Direction (Higher Better / Lower Better). All required.
Custom KPI delete
Red × button on the row. No confirmation. Removes from client.customKpis immediately. Historical entry data for that KPI stays in storage but becomes unreachable from the UI.
Custom KPI ID format
Generated as c_<random>. Stored on entries by this ID. Renaming a custom KPI doesn't change its ID — historical data follows.

Planned Changes (for rebuild)
Add "Working Hours" to capacity groups (By Labor Hours method)
Add a Working Hours/Wk field alongside the existing Capacity Hrs/Wk on each employee row of capacity groups using the By Labor Hours method. Capacity = produced-hours target. Working Hours = actual scheduled time on the clock.
Example: Team A — Capacity: 120 hrs/wk · Working Hours: 135 hrs/wk. (3 people × 45 hr schedule = 135 working; produces 120 of valued output.)
Scope: Field appears on the employee table only when the group's method is "By Labor Hours." Other methods don't have an Efficiency calculation, so the field has no meaning there.
Storage: New field on each employee object inside the capacity group, e.g. weeklyWorkingHours.
Label clarity: Rename existing "Hrs/Wk" column to "Capacity Hrs/Wk" so the distinction is unambiguous.
Labor Efficiency — move to Operations, redefine
Move Labor Efficiency from Team to Operations. Redefine as Produced Hours ÷ Working Hours. Measures how fast the work got done this week.
Formula: sum of group's Labor Hours Completed (produced) ÷ sum of working hours across employees in that group. Per group, then rolled up if multiple groups.
Applies only to: Capacity groups using By Labor Hours method. Other methods don't have produced/working hours to compare; no tile.
Distinction from Utilization: Efficiency = output vs actual time on the clock. Utilization = output vs reasonable target capacity. Same numerator, different denominators. A team can be highly efficient but under-utilized, or highly utilized but inefficient.
Today's behavior: Labor Efficiency is defined in KPIS but never actually rendered. Activates as a real Operations tile after this change.
Manual % method — one-time setting, not a weekly input
Today, capacity groups using Manual % require the coach to enter a utilization % on every weekly entry. Change so Manual % is a single number set once in Settings (per capacity group). The dashboard tile displays that number every week, unchanged, until the coach updates the setting.
Settings UI: Manual % capacity group has a single "Utilization %" field in the group config. No employee/department list needed.
Weekly Entry UI: Manual % groups show no field. Tile is informational only.
Storage: Move utilPct from entry.cgData[id] to capacityGroup.staticUtilPct.
Use case: Coach has decided "Production runs at 88% on average" — set it and stop typing.
Drop "By Working Hours" as a capacity method
Remove the By Working Hours method from the list of capacity tracking options. Its math (produced ÷ FTE × hrs/wk) is now covered by the combination of By Labor Hours (utilization vs capacity) + Labor Efficiency (produced ÷ working hours).
Remaining methods: Manual %, By Time Slots, By Labor Hours, By Revenue ($), By Headcount. (5 methods, down from 6.)
Migration: Demo seed and any existing groups using By Working Hours need to be either re-set as By Labor Hours or recreated. None in current demo data, so no migration concern there.
Clean up duplicated weeklyHoursPerFTE
Today this field exists at both the client root and inside each capacity group, with no clear authority. Remove the client-root version. The per-group version becomes the only source.
Use: The per-group field powers calculations only for methods that need it (Headcount). With "By Working Hours" gone (see above), the only remaining method that uses it is Headcount.
Working Hours field (different): The new per-employee Working Hours field replaces this for Efficiency calculations. Don't confuse the two.
Remove legacy capacity system entirely
Drop the pre-groups capacity fields from the client root: capacityMethod, slotDuration, employees, departments, weeklyRevCapacity, headcountCapMethod. They're defined and have logic in calcUtil but no UI exposes them — pure dead weight.
Effect: getEnabledKpis and calcUtil get a lot simpler. Conditional rendering branches in EntryView and DashView for "no groups configured" disappear because every client always has at least the empty capacityGroups array.
Also drop: hiddenKpis field — defined in client defaults, never read anywhere.
Client access to Settings — partial editability
Today, clients have full edit access to Settings — they can toggle KPIs, change industry, modify capacity groups, delete custom KPIs. This is risky: clients can silently change what's tracked, create gaps in their own data, or orphan historical entries. Restrict client editing to fields that are genuinely "theirs."
Client-editable fields: Contact Name, Company Name.
Coach-only fields: Email (login key — see Password Reset below), Shared Folder Link, Industry, Active KPI toggles, Capacity Groups (entire section — definitions, employees, working hours, capacity hours, methods), Custom KPIs (add / edit / delete).
UX: Coach-only fields render in client view as read-only (greyed inputs, no edit). Add a small note: "Contact your coach to update these settings." Save button only writes the editable subset.
Coach view: All fields editable as today.
Industry-related logic: Since Industry is now coach-only and the 7 standard industries are removed (Doc 02 planned change), the Industry dropdown is purely a list of coach-defined custom industries.
Add password reset flow (coach-generated reset codes)
Today there's no way for a client to recover a forgotten password — and since email infrastructure isn't part of the portal, traditional reset-link emails aren't possible. Add a coach-generated, single-use reset code system that reuses the invite-code pattern.
Coach action: Coach Admin client card gets a "Reset Password" action. Click generates a random 6-char code, displays it for the coach to relay to the client (text, email, in-call). Code is stored on the client record with a 24-hour expiration.
Client flow: Login page gets a "Forgot password?" link. Clicking it shows a form: Email + Reset Code + New Password. On submit, validates the email/code pair, sets the new password, marks the code consumed.
Storage: New fields on client record — resetCode, resetCodeExpiresAt. Cleared on successful reset or expiration.
Security notes: Single-use (consumed on success). Expires after 24 hours. Generating a new code invalidates any prior unused code. Coach-only — clients can't trigger reset for themselves (this preserves the coach-as-gatekeeper model, and there's no email channel anyway).
Future: If self-service reset is wanted later, the natural addition is security questions captured during activation. Out of scope for now.
KPI dependency model — auto-enable inputs, cascade-off with confirmation
Today, auto-derived KPIs (Conversion Rate, Avg Repair Order, etc.) only render when their inputs happen to be toggled on — and the dependency is invisible. Coach toggles random KPIs and silently fails to get the calculated tile they wanted. Replace with an explicit dependency model.
Auto-derived KPIs are now in the toggle list. Coach picks "Avg Repair Order" directly. The system handles inputs.
Toggling an auto-KPI on: auto-enables every required input that's currently off. Both the dependent and the inputs render as full tiles.
Toggling an input off (when something depends on it): Cascade. Show confirmation: "This will also disable Avg Repair Order (which requires Jobs Completed)." On confirm, both toggle off.
Toggling an auto-KPI off: Inputs that were auto-enabled stay on. The coach didn't ask to lose them — they're real KPIs in their own right and toggleable on directly anyway.
UI feedback when auto-enabling: Both — input toggles visibly flip on (briefly highlighted) AND an inline message under the auto-KPI: "Also enabled: Jobs Completed."
Dependency hints in toggle list: Each auto-KPI shows what it requires, e.g. "Avg Repair Order — requires Jobs Completed." Skip the hint when the only dependency is an always-on financial (Revenue, COGS, Gross Profit, GP Margin) — those are guaranteed present, calling them out is noise. (No current KPI hits this case; rule is forward-looking.)
Sales section restructure — flat (no Estimating subsection)
With the KPI splits below, the Estimating subsection is unnecessary. Sales becomes a single flat list of tiles. Pipeline subsection still exists as its own grouping (Pipeline Value, Pipeline Deals, Avg Deal in Pipeline).
Today: Sales splits into Main → Estimating → Pipeline three subsections.
New: Sales splits into Main → Pipeline. Two subsections only.
Drag-reorder behavior (from Doc 03): Subsection order within Sales can still be reordered, just only Pipeline is left to move.
Split "Estimates / Contracts Won" into two KPIs · rename auto-KPIs
The current "Estimates / Contracts Won" tile conflates two different things. Split into two separate, individually-toggleable KPIs. Plus rename Revenue per New Client to reflect its new formula.
New KPI: Contracts Won ($). Sales category. The closed-deal headline number. Sum.
New KPI: Estimates Won ($). Sales category. Distinct from Contracts Won — coach picks whichever fits the client's terminology. Sum.
Renamed: Revenue per New Client → Contract Value per New Client. Operations or Sales — confirm placement. Formula changes too — see #12 below.
Renamed: "Estimates Written – Target $" → "Estimates Written ($)". Per Doc 03 planned change. Just dropping the "Target $" wording.
Storage note: Splitting newContractsDollars into two distinct KPI ids requires picking new ids and migrating any historical entry data. For the rebuild, fresh start — no migration needed.
Contract Value per New Client — formula change
Today: Revenue per New Client = Revenue ÷ New Clients. But Revenue includes everything — services, parts, repeat work — making this a poor measure of new-client deal size. Change the formula to use Contracts Won.
New formula: Contract Value per New Client = Contracts Won ($) ÷ New Clients.
Dependencies: Toggling Contract Value per New Client on auto-enables both Contracts Won AND New Clients (per the dependency model in #9).
Inverted from current: The old name ("Revenue per New Client") and new name use different numerators, so any historical comparison is apples-to-oranges. Worth flagging in any export/migration.
Move capacity & utilization targets fully into Budget & Goals
Today, the goal % (or $) for each capacity group lives in Budget & Goals as budget.capacityGroupGoals. Confirming that's the right home — keep it there. Settings owns the structural definition (group name, method, employees, capacity hrs, working hrs); Budget & Goals owns the target numbers.
Rationale: Setup (who/what/how) changes rarely. Targets get reset annually alongside revenue goals. Different cadences belong in different places.
Manual % exception: The static utilization % (per the Manual %-as-setting change in #3) lives in Settings — it's a configuration value, not a target. The Budget & Goals card just doesn't show a goal field for Manual % groups (no target needed; the value IS the displayed number).
Auto-derived KPIs get their own goal fields
Today, auto-derived KPIs (Conversion Rate, Avg Repair Order, Avg Pipeline Deal, Contract Value per New Client, Avg Estimate Value, Avg Transaction Value, Sales Close Rate) don't get individual goal fields in Budget & Goals — their tiles inherit color logic from the inputs. Change so each auto-derived KPI gets its own goal field, settable independently.
Why: A coach might want "Avg Repair Order ≥ $400" as a target distinct from "Jobs Completed ≥ 30/week" — an auto-derived KPI is a real number with its own meaning, not just a side-effect of the inputs.
Format: Goal field's format (#, $, %) follows the KPI's own format, just like input KPIs.
Coloring: Auto-KPI tile colors against its own goal, not its inputs'.
Toggle-off preserves data — codify as intentional behavior
Already the existing behavior, but make it explicit and durable: toggling a KPI off in Settings is a visibility change, never a destruction change. All data is preserved.
What's preserved on toggle-off:
· Historical weekly entry values for that KPI — all of them, every week.
· Goal value for that KPI in budget.goals[id].
· Custom KPI definition itself (if applicable).
Toggle back on: Tile reappears, historical data shows in History view, goal coloring resumes, weekly entry field returns. Nothing was lost.
Mental model: Toggle off = "hide from my dashboard." Need to actually delete data → must be a separate, explicit, confirmed action.
Custom KPI delete — add confirmation with cascade warning
Today, the red × on a custom KPI deletes it instantly with no confirmation, orphaning all historical entry data. Add a confirmation dialog that surfaces the cost.
Confirmation copy (when historical data exists): "Deleting NPS Score will permanently remove the KPI definition and unlink 47 weekly entries that contain values for it. The entry data won't be visible anywhere after deletion. To hide this KPI without losing data, toggle it off in [where toggles live] instead."
Confirmation copy (no historical data): "Delete NPS Score? This custom KPI has no historical data."
Storage cleanup: Removes the KPI from client.customKpis. Optionally also strips the orphaned values from every weekly entry, OR leaves them in place as inert. Either is defensible — leaving them is safer for any "undo" future.
Coach-only: Per #7, custom KPI editing is coach-only anyway, so this confirmation is for the coach.
Re-balance the top bar — client first, branding to footer (carry-forward from Doc 03)
Same change as on every client-facing page. Client company name becomes the primary title; "The Good Plans Co" branding moves to a small footer.
Cross-doc: persistent saved state & Cancel pattern
The Save Settings buttons (top-right and bottom-right) follow the portal-wide Save/Cancel pattern documented in Doc 06.
Persistent "Saved ✓" state: after a successful save, the button stays green and reads "Saved ✓" until the form is changed or the user navigates away. Replaces the current 2-second flash.
Cancel button paired with Save: add a Cancel button next to each Save Settings button. Reverts the form to the most recently saved state — including company info, industry selection, KPI toggles, capacity groups, and custom KPIs.
Unsaved-changes guard: navigating away (top-nav clicks, Logout) with unsaved changes opens the Save / Discard Changes / Stay Here dialog.
Industry change consideration: changing the industry resets KPI defaults (current behavior). With the saved-state pattern, the change becomes "unsaved" — Cancel reverts both the industry and the KPI toggles back to their previous saved state.
See Doc 06 for the full spec. This is just the cross-reference to keep all surfaces consistent.
Shared Drive button — top-bar shortcut on every client page
The sharedFolderLink field is captured but never surfaced in the UI. Make it a clickable shortcut so clients can jump to their shared materials (Google Drive, Dropbox, OneDrive, etc.) from anywhere in the portal.
Button placement: top bar of every client-facing page — Dashboard, Weekly Entry, Budget & Goals, History, Settings. Sits alongside the nav links, opens the link in a new tab.
Label: "Shared Drive" — clear, neutral, familiar terminology that matches what most clients call their cloud storage. Avoids ambiguity with documents inside the portal.
Edit access: coach-only. The link is set in Settings (per the "Client access to Settings — partial editability" planned change above). Clients see the field as read-only in their Settings view — they can't change where the button points.
Empty state: if no link is set, the button doesn't render. No empty button, no broken link.
Coach view: button works the same way — clicking opens the same shared drive the client sees, useful for the coach to grab files during a session.
Top bar interaction with branding flip: per Doc 03's "Re-balance the top bar" change, client name becomes the primary title. The Shared Drive button sits in the same row as the nav, alongside Logout. Order suggestion: client name (left) · nav links · Shared Drive · Logout (right).
Note: current code behavior (above) is unchanged for now. These are notes for the eventual rebuild, not edits to apply today.
